### 1 of 44 — HIGH — Any collected title containing `<!--<script>` blanks the whole page

**What.** Both HTML builders inject their collected JSON into a `<script type="application/json">`
block and defend it with a single replacement, `</` → `<\/`. That stops a
literal `</script>` but not `<!--<script>`, which moves the HTML tokenizer into
script-data-double-escaped state so the template's own closing tag no longer
closes the block. Everything after it, including `<div id="app">`, is swallowed
as script text. Found by trudy in `skills/brief-portfolio/scripts/build.py:47-48`
and `skills/debrief-meeting/scripts/build.py:140-144`.

**Evidence.** `confirmed`. Control (the defended vector, `</script><img …>`)
mounted fine: `appDivPresent = true, imgTagsInDoc = 0`. Probe with the title
`benign <!--<script> tail`, same file, exit 0 and no warning from the builder:
`appDivPresent = false`, `payloadJsonParses = false :: Unexpected non-whitespace
character after JSON at position 417`, `h1 = null`. Reproduced through the
meeting tool's real two-stage pipeline from a plain-text transcript line.
**No script execution was achieved** — the `</` escape does hold against
tag-closing — so this is loss of the artifact, not XSS.

**If unchanged.** The brief and the debrief are single-file HTML artifacts a
human opens to make decisions. One unlucky commit subject, issue title or
spoken sentence renders a blank white page with no error, and the builder
reports success. Reach is real but not fully executed: `collect.py` stores
third-party text verbatim from `gh issue list`, `gh pr list` and `gh search prs`
(line 334, which spans repos the operator does not own). That collector hop was
read, not run. Stable, not compounding, but it recurs whenever the string
appears.

**Options.**
- **(Recommended) Escape for the script context, not the tag.** `json.dumps(...).replace("<", "\\u003c")`.
  `<` is valid JSON inside strings, survives `JSON.parse`, and kills
  `</script`, `<!--` and `<script` in one rule. Benefit: one line, both files,
  closes the class. Drawback: it re-encodes every `<` in the payload, so the
  built file grows slightly and a future reader may not see why the rule is
  there without the comment. Effort: S. Could break: nothing observed — the
  page reads the payload through `JSON.parse`, which decodes `<` back.
- **Sanitise the collected text at the collector.** Strip or replace angle
  brackets in `collect.py` and `parse.py` before they reach `data.json`.
  Benefit: the hostile text never enters the store. Drawback: lossy — a repo
  genuinely named with a bracket, or a transcript line quoting HTML, is
  silently corrupted, and it leaves the builder still unsafe for any future
  input path. Effort: M.
- **Move the payload out of the HTML into a sibling `.json` file.** Benefit:
  no escaping problem can exist. Drawback: destroys the product's defining
  property — a single self-contained file you can mail or open from disk.
  Effort: L.
- **Accept or defer.**

**Recommendation: the first.** Strongest honest reason against: it is a
one-character fix to a defect whose only proven consequence is a blank page,
so it is easy to under-test — pair it with the regression test rather than
shipping the replace alone.

### 2 of 44 — HIGH — `trash_untracked` moves files out of `dev/local/` and `.git/` when the path carries a `../`

**What.** `trash_untracked.py` checks containment on the *resolved* path but
checks every protection on the *raw* string, then moves the *unresolved* path.
A `sub/../` prefix therefore passes the containment check, fails to match
`PROTECT_PREFIXES`, and still lands on the protected file. Found by trudy in
`skills/brush/scripts/trash_untracked.py` (containment at 101-102, protection
at 57, move at 75).

**Evidence.** `confirmed`. Same file, two spellings, opposite outcomes:
`dev/local/tmp/marker.json` → `{"refused": [{"reason": "protected path (dev/local, docs, .git)"}]}`;
`sub/../dev/local/tmp/marker.json` → `{"moved": [{"trash": "dev/local/.trash/2026-08-31/sub/../dev/local/tmp/marker.json"}]}`,
and the original is gone. The same pair reproduced against a planted `.git/`
marker in one invocation, one spelling refused and the other moved.

**If unchanged.** The three things this script exists to never touch —
`dev/local/`, `docs/`, `.git/` — are reachable by anything that hands it a
path with a `..` segment, which shell completion, a script joining relative
paths, or a careless operator all produce. Damage is survivable because it is
trash-first, but the restore is broken too: the manifest records the
unnormalised destination while `mkdir(parents=True)` normalised it away, so
`.../<date>/sub/` never exists and the docstring's "mv the file back per the
manifest line" cannot work for these rows. Stable per invocation; compounds
only in that a bad row is permanent in the manifest.

**Options.**
- **(Recommended) Normalise once, then use one path everywhere.** After the
  `is_relative_to` check, `rel = os.path.relpath(p, root)`, and pass that
  `rel` to `veto_reason`, `relocate` and `note_manifest`. Benefit: fixes the
  bypass and the broken manifest row together, and removes the raw/resolved
  split that caused both. Drawback: changes the `path` string the JSON output
  reports, so any caller parsing that output sees normalised paths now.
  Effort: S. Could break: a caller that round-trips the reported path back in
  — none found in this repo.
- **Reject any path containing a `..` segment outright.** Benefit: two lines,
  no normalisation semantics to get wrong. Drawback: refuses legitimate
  callers that pass a normalisable path, and leaves the manifest bug standing.
  Effort: S.
- **Give the script a dry-run and require it first.** Benefit: prevents the
  class — an operator sees what would move before it moves. Drawback: does not
  fix the bypass at all, only makes it visible; and it changes the calling
  convention for `brush`. Effort: M. (This is finding 44 on its own merits.)
- **Accept or defer.**

**Recommendation: the first.** Strongest honest reason against: it silently
changes the reported `path` field, and if anything downstream keys on the
caller's exact spelling, that breaks without a loud signal.

### 3 of 44 — HIGH — `build.py --dir <somewhere>` reads from there but overwrites the dashboard in `$HOME`

**What.** `--dir` moves where the builder reads its inputs, but `--out`'s
default is derived from the home directory rather than from `args.dir`, so a
build from a scratch directory silently replaces the real portfolio brief.
Found by walter in `skills/brief-portfolio/scripts/build.py:17-19`.

**Evidence.** `confirmed`, and it fired on first use during this run. Inputs
came from scratch (the `epics.json` warning names the scratch path), output went
home: `WARN: /…/T/agoge-walter/j4/epics.json not found` then
`wrote /Users/bob/.local/share/agents/portfolio-brief/portfolio-brief.html (345 kB)`.
The operator's real 691295-byte file was replaced. The sibling skill gets this
right — `debrief-meeting/scripts/build.py --help` prints
`--out OUT   output html (default: <dir>/debrief.html)` — so only
`brief-portfolio` decouples the two.

**If unchanged.** Anyone testing a build, or a script building into a temp
directory, destroys the live dashboard with no warning and exit 0. It already
happened once this run. `--dir` is not documented in `SKILL.md` at all, only in
the module docstring, which says "defaults under
`~/.local/share/agents/portfolio-brief/`" and hides the decoupling — so the
documentation actively misleads. Stable, high likelihood on any non-default use.

**Options.**
- **(Recommended) Default `--out` off `--dir`.** `ap.add_argument("--out", default=None)`
  then `out = Path(args.out) if args.out else workdir / "portfolio-brief.html"`.
  Benefit: matches the sibling skill, makes `--dir` self-contained, one place.
  Drawback: a caller who today passes only `--dir` and *relies* on the home
  output would change behaviour — unlikely but unannounced. Effort: S.
- **Refuse `--dir` without an explicit `--out`.** Benefit: no silent behaviour
  change for anyone. Drawback: breaks the ergonomic case the flag exists for,
  and pushes the burden onto every caller. Effort: S.
- **Leave the coupling, document it loudly in `SKILL.md` and the `--dir` help.**
  Benefit: zero behaviour change. Drawback: keeps a footgun that has already
  fired once, and documentation does not stop a script. Effort: S.
- **Accept or defer.**

**Recommendation: the first.** Strongest honest reason against: it is a real
behaviour change to a default, so a wrapper somewhere that passes `--dir` and
expects the home file will start writing elsewhere silently.

### 4 of 44 — HIGH — `braid --check` says "0 drift" while dangling skill links sit in the farm forever

**What.** `.braid-state.json` is the only record of which links braid owns. Any
link on disk the state does not name is invisible to braid permanently: not
cleaned, not reported, not counted as drift. Found by heidi in
`src/agent_skills_braid/cli.py`; `AGENTS.md` names `braid --check` as the health
gate after every skill edit.

**Evidence.** `confirmed`, two independent triggers. (a) A mid-sync abort:
links are created in the first loop but state is written only at the end
(`cli.py:381`), and a refusal in the cleanup loop (`cli.py:322`) skips the write
entirely — `ON DISK … probe-orphan: True`, `IN STATE union probe-orphan: False`.
(b) State file lost, then a re-sync rewrites it without the orphan:
`check 0 braid: 0 linked, 74 current, 20 ignored, 0 removed, 0 backed up, 0 drift`
while `DANGLING …/skills/probe-orphan exists_target=False lexists=True` for two
links.

**If unchanged.** The one command meant to catch a broken skill farm certifies
it clean. A dangling link means a skill silently does not load on any host that
reads the union, and nothing tells the operator. This compounds: every abort and
every state loss adds another permanently invisible orphan, and the count only
ever grows.

**Options.**
- **(Recommended) Reconcile against the filesystem, not only against state.**
  After the desired/previous loops, scan `destination_root` for symlinks
  resolving inside a known source root that are neither desired nor in
  `previous`, and report them as drift. Benefit: catches both triggers and any
  future one, because it stops trusting the manifest as the sole truth.
  Drawback: a scan of the destination root on every `--check`, and it must not
  claim ownership of links braid did not create — getting that predicate wrong
  turns a health check into a deleter. Effort: M.
- **Write state incrementally, so an abort leaves an accurate manifest.**
  Benefit: fixes trigger (a) at the root and is cheap. Drawback: does nothing
  for trigger (b), and a partial write is its own hazard given finding 34.
  Effort: M.
- **Report a missing or unreadable state file as a hard error rather than an
  empty state.** Benefit: trigger (b) can no longer start. Drawback: a genuinely
  first-ever run on a new machine now fails and needs a `--init` escape hatch;
  and trigger (a) survives untouched. Effort: S.
- **Accept or defer.**

**Recommendation: the first.** Strongest honest reason against: the ownership
predicate is the whole risk. A filesystem reconciliation that mis-identifies an
operator's hand-made link as braid's turns `--check` from silent into
destructive, which is worse than the bug.

### 5 of 44 — HIGH — A corrupt review queue is indistinguishable from a finished one

**What.** `docket.load()` does `json.loads(p.read_text())` with no validation and
no error handling, so every malformed queue produces exactly the signature
`SKILL.md` step 2 defines as "the queue is drained — stop and report": exit 1
with empty stdout. Found by heidi in `skills/distil-memory/scripts/docket.py`.

**Evidence.** `confirmed`. Five corruption classes, all identical from the
driver's point of view — `next  exit=1  stdout=''` for truncated JSON, a missing
`entries` key, non-dict entries, a top-level list, and an empty file. The
documented command is `docket.py next > entry.json`, which redirects stdout only,
so the traceback on stderr never reaches the caller. The cross-check `SKILL.md`
step 7 prescribes lies too: `cursor  exit=0  stdout='0'` over broken state.

**If unchanged.** A sitting reports "all proposals reviewed" when in fact none
were readable, and the operator has no signal that anything is wrong. Braid, in
this same repo, validates its state file and prints one actionable line per
corruption class, so the pattern to copy is already here. Stable per corruption
event; the harm is that undecided proposals sit forever while the tool says it
is done.

**Options.**
- **(Recommended) Validate in `load()` and separate the exit codes.** Raise
  `QueueError` with a distinct message per class, give `next` exit `2` for
  "queue unreadable" versus `1` for "nothing left", and say so in `SKILL.md`
  step 2. Benefit: the two states become distinguishable at the only place the
  driver looks. Drawback: exit `2` is a contract change — anything scripting
  `docket.py next` on `exit != 0` needs updating. Effort: M.
- **Validate in `load()` but keep exit 1, and print the reason to stdout.**
  Benefit: no exit-code contract change. Drawback: stdout is the entry payload's
  channel, so a reason printed there corrupts `entry.json`. Effort: S.
- **Copy braid's `_load_state` shape wholesale — a schema check plus a typed
  error — and reuse it for both stores.** Benefit: prevents the class across
  both JSON stores in the repo. Drawback: a shared validator across two
  unrelated skills is coupling the repo does not otherwise have. Effort: M.
- **Accept or defer.**

**Recommendation: the first.** Strongest honest reason against: the exit-code
change is a real break, and if any wrapper treats non-zero as "drained" it will
now loop or stop in a new way.

### 6 of 44 — HIGH — The review queue lands wherever the shell happens to be, so one proposal set can be queued and written twice

**What.** `docket.py` exposes no queue-path flag. `_resolve_path(None)` walks up
from **`Path.cwd()`** to the nearest `.git` and lands on
`<that root>/dev/local/audit-results/distil-memory-queue.json`. `save
--proposals-dir` takes an explicit proposals directory but ignores it when
choosing where the queue goes. Found by heidi in
`skills/distil-memory/scripts/docket.py:18-27`.

**Evidence.** `confirmed`. Running `save --proposals-dir <repoA>/proposals` from
repo B wrote the queue into repo B while repo A's queue kept its own 2 entries.
Cursors then disagreed: `cursor from A: 1 | cursor from B: 0`, and repo B's
`next` re-offered a proposal already written to disk from repo A. The
subsequent write failed: `exit 1 | .../store/memory/scratch-fact-one.md already exists`.
A cwd with no `.git` above it silently opens a third queue.

**If unchanged.** Two failure shapes, both bad. Running the walkthrough from the
wrong directory reports "drained" while undecided proposals sit in another
repo's queue (finding 5's symptom by a second route). Worse, a duplicate queue
re-offers a decided proposal, and `SKILL.md:206` tells the operator to resolve
the resulting "already exists" by renaming through the edit path — which would
put a second copy of the same memory in the plane under a different name.
Compounds: every extra queue is permanent and invisible.

**Options.**
- **(Recommended) Add `--queue PATH` to every subcommand and default `save`'s
  queue off `--proposals-dir`.** Benefit: the queue follows the proposals it
  describes, which is the only coupling that makes sense, and an explicit flag
  covers every other case. Drawback: existing queues already sitting in the
  wrong repos are not migrated by this and must be found by hand. Effort: M.
- **Resolve the queue from the proposals directory only, with no flag.**
  Benefit: smaller surface, impossible to point wrong. Drawback: `next`,
  `decide` and `cursor` have no `--proposals-dir` today, so they would all need
  one anyway — the flag arrives by the back door and less clearly. Effort: M.
- **Keep cwd resolution but refuse to run when no `.git` ancestor exists, and
  print the resolved queue path on every command.** Benefit: cheap, and makes
  the divergence visible the moment it happens. Drawback: does not stop it, only
  narrates it; two repos each with a `.git` still diverge silently. Effort: S.
- **Accept or defer.**

**Recommendation: the first.** Strongest honest reason against: it does not
clean up the queues already scattered by the current behaviour, so shipping it
alone can leave the operator believing the problem is over while a stale queue
still holds undecided proposals.

### 7 of 44 — HIGH — `write.py` puts a malformed memory file on disk, then crashes, and the documented recovery cannot succeed

*Merged: heidi (integration) and wendy (release) raised this from different
ends — the half-applied store and the shipped CHANGELOG claim it contradicts.*

**What.** `write.py:125` calls `append_pointer` **outside** the try/except that
guards `write_memory`, and `write_memory` never parses frontmatter. Any entry
whose `file_text` is malformed is written to disk first and blows up second.
The same unguarded shape appears in `docket.py` at `main`'s `read_text` (line
211) and in `_save_from_proposals_dir` (line 177). Found in
`skills/distil-memory/scripts/{write,docket}.py`.

**Evidence.** `confirmed`. `write.py write` printed the written path, then
`ProposalError: file does not open with a --- frontmatter marker` as a raw
traceback, with `on disk: ['probe-partial.md']` and `MEMORY.md` never updated.
Three shipped claims break at once: `CHANGELOG.md:27-29` says these commands
"report queue and write errors … instead of raising a Python traceback";
`SKILL.md:193-195` repeats it; and `SKILL.md:194-198`'s "re-run the same command"
recovery returns `exit 1 | ... already exists`. `SKILL.md:204-207` then
mis-diagnoses that message as another proposal claiming the filename — nothing
else claimed it; the same proposal did, on its own crashed run. Two more
routes reproduce the traceback: `docket.py decide --file <missing>` and
`docket.py save --proposals-dir <missing>`.

**If unchanged.** The approval walkthrough dumps a Python traceback on a
mistyped path, and a crashed write leaves an unindexed, malformed memory file in
the store while the queue records the proposal as `kept`. Every documented way
out is closed: `decide` is terminal, `next` skips decided entries, and the
re-run is refused. The operator must hand-edit the store. Stable, and each
occurrence leaves permanent debris.

**Options.**
- **(Recommended) Validate before writing, and guard the whole operation.**
  Call `proposal.parse_frontmatter` up front in `write_memory`, move
  `append_pointer` inside `main`'s `except WriteError`, and wrap the two
  `docket.py` `read_text`/`json.loads` sites in `except (OSError, json.JSONDecodeError)`
  returning 1 with the message on stderr. Benefit: closes all four sites and
  makes the shipped claim true. Drawback: touches two modules and four call
  sites, so it is the largest of these options and needs the whole distil-memory
  suite re-run. Effort: M.
- **Guard `append_pointer` only.** Benefit: smallest change, stops the store
  being half-written. Drawback: leaves the `docket.py` tracebacks standing, so
  `CHANGELOG.md:27-29` stays false for two of its four routes. Effort: S.
- **Validate at `docket.decide --file` instead, so a malformed file never
  enters the queue.** Benefit: stops the bad input at the boundary, which is
  where validation belongs. Drawback: does not fix the unguarded
  `append_pointer`, so any *other* failure there (an unreadable `MEMORY.md`, a
  full disk) still half-applies. Effort: S.
- **Accept or defer.**

**Recommendation: the first.** Strongest honest reason against: it is the
broadest change in this report's HIGH set, and bundling the `write.py` and
`docket.py` halves means one review covers two modules — splitting it into two
commits would be easier to verify.
